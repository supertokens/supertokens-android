## Constraints to carry into import work

- **Second restart:** an accepted lenient import must remain readable after schema-1 persistence and reload. Relaxing the import entry point alone is insufficient. At **supertokens/supertokens-android @ eda605ba8453bc716b82b83c04628a4c0ac4ba3e**, inspected from committed code on 2026-10-29, [`importLegacyLocked`](https://github.com/supertokens/supertokens-android/blob/eda605ba8453bc716b82b83c04628a4c0ac4ba3e/app/src/main/java/com/supertokens/session/SessionState.java#L200-L229) writes schema 1 and constructs a snapshot; [`snapshotFromRecord`](https://github.com/supertokens/supertokens-android/blob/eda605ba8453bc716b82b83c04628a4c0ac4ba3e/app/src/main/java/com/supertokens/session/SessionState.java#L875-L930) revalidates AVAILABLE records, including versioned identity consistency. Acceptance evidence must include candidate→candidate restart for each lenient row.
- **Sequential raw setters:** preserve intermediate credentials until the historical setter sequence completes; interpreting a partial tuple as absent must not erase tokens needed by the next setter. At the same commit, [`legacyStorageChanged`](https://github.com/supertokens/supertokens-android/blob/eda605ba8453bc716b82b83c04628a4c0ac4ba3e/app/src/main/java/com/supertokens/session/SessionState.java#L386-L412) reloads/imports after raw changes, while [storage writes](https://github.com/supertokens/supertokens-android/blob/eda605ba8453bc716b82b83c04628a4c0ac4ba3e/app/src/main/java/com/supertokens/session/SharedPreferencesSessionStorage.java#L83-L97) put or remove each credential. Exercise actual public setter sequences, not only atomic fixture seeding.
- **Marker limits:** the initial design concern is now supported by the 2026-10-29 oracle report from `ses_e78448ed1ffesylJ70UuHlkgEn`: raw/access-only edits did not update the marker, a same-time marker collision was observed, and schema-1 rollback metadata was preserved. See [characterization provenance](baseline-2026-10-29.md#oracle-characterization-and-current-slice-reports). Marker equality cannot establish that credentials are unchanged.
- **Fingerprint limits:** a tuple fingerprint can show disagreement with recorded evidence, but cannot establish whether an older SDK changed the tuple or storage was corrupted. A mismatch alone does not approve lenient re-import. This is an inference about provenance, not proof of either cause.
